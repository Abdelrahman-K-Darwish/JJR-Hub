How the app works

The application tier as flows — from the big picture down to each feature. The app is a permission-aware records-and-orchestration layer: it authenticates you, decides what you may see, owns the structured records, and orchestrates the rest. Documents and editorial pages are surfaced, never built here.

Overview

How a request works

Every page calls the app. The app authenticates you, scopes the response, and fetches from the back rooms — it owns records and orchestration, not documents.

Everything routes through the permission engine

No feature re-implements access. Each one asks the same two functions — that is why the app is smaller than the hub looks.

Access spine

The permission check

can(user, action, resource) — leadership and admin pass; otherwise you need a role on that specific resource that permits that action. Denial is a dignified path, not a dead end.

Scoped read — filter first, then fetch

Every list and count on every page. Ask the engine for the allowed set, query only within it, aggregate over it, enrich last. Nothing outside your scope is ever sent.

Request access and review

The Deny branch turned into a loop the whole hub reuses. Approval simply inserts an AccessGrant — the exact table the check already reads — so the next request just passes.

Content and work

Native content — discussions, comments, lessons

Reading, posting, and moderating are three actions passed to the same check. One polymorphic Post table; soft-remove is moderation; attachments are SharePoint pointers.

Tracked work — the action state machine

A record with a legal set of transitions and an owner. Create and assign is a manage check; advancing is the assignee or a manager; overdue is derived, never stored.

Messaging and events

Targeted messaging — authoring

One engine for Action Needed, Notifications, and PMO announcements. Author, target an audience, store once. A prominence flag decides whether it becomes a banner or a bell.

Targeted messaging — delivery

Authored once, but each recipient has their own state. On load the engine finds messages targeting you that are still live; acting only ever touches your own copy.

Orchestrated events — the meeting lifecycle

The app owns the record and drives the lifecycle; Graph makes the calendar event and invites, Power Automate emails the notes, leadership soft-archives. Both side-effects sit behind seams.

Profile and build

The profile renders three faces

The server resolves who is looking relative to the owner and sends only the permitted sections. Squad-only sections are omitted from the response — never hidden client-side.

The walking skeleton — the first slice

The smallest path that proves the whole architecture: auth, engine, scoped read, and SharePoint-via-Graph, deployed end to end. Build this first, then widen feature by feature.

Build order

Build in dependency order, as vertical slices

Stand up the walking skeleton first — one thin path deployed end to end — then add each feature alongside it. The hard seams (identity, engine, content) are proven once, up front.

  1. Permission engine  foundation — everything calls can() / scopeFilter()
  2. Scoped read  first consumer — projects, milestones, counts, health
  3. Request-access + review  the Deny branch; approval writes an AccessGrant
  4. Native content  discussions, comments, lessons learned
  5. Tracked work  action tracker; onboarding progress
  6. Targeted messaging  Action Needed + Notifications + announcements
  7. Orchestrated events  Meeting Hub — Graph + Power Automate behind seams
  8. Cross-cutting  edit mode; profile three-face render — recombine 1–7

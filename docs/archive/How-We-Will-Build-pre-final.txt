# 4. Map the Systems

Before React architecture, we document where information will eventually come from.

Example:

```text
React Hub
    │
    ├── Application Backend
    │      └── Database
    │
    ├── Microsoft Entra ID
    │
    ├── SharePoint
    │
    ├── Microsoft Graph
    │
    ├── Planner
    │
    └── Other external systems
```

For every data type we determine:

* Who owns it?
* Who can read it?
* Who can change it?
* Where is it stored?
* Is React only displaying it?
* Does the backend enforce access?

This prevents Claude from putting business logic in random components.

# 5. Identify Workflow Candidates

This is where we decide what deserves an SVG.

## We DO NOT create an SVG for every page.

For example:

```text
User opens About page
↓
Page loads
```

Does not deserve a workflow.

But this does:

```text
User requests project
↓
Check existing access
↓
No access
↓
Create request
↓
Approver reviews
↓
Approve / Reject
↓
Permission updated
↓
User receives access
```

That deserves a workflow.

---

# 6. My Rule for Deciding Whether a Workflow Needs Documentation

I test each process against **7 questions**.

### 1 — Are multiple roles involved?

Example:

```text
Consultant → Project Lead → PMO
```

If yes → workflow candidate.

---

### 2 — Is there a decision?

Example:

```text
Does user have access?
       ↓
     Yes / No
```

If yes → workflow candidate.

---

### 3 — Does data change?

Examples:

* Create project
* Update profile
* Join community
* Approve access
* Complete onboarding
* Submit lesson learned

If yes → workflow candidate.

---

### 4 — Is security involved?

Examples:

* Authentication
* Authorization
* Restricted page
* Project-scoped data
* Leadership-only area

If yes → usually **must document**.

---

### 5 — Does the process cross systems?

Example:

```text
React
  ↓
Backend
  ↓
Microsoft Graph
  ↓
SharePoint
```

If yes → workflow candidate.

---

### 6 — Can the workflow fail?

Example:

```text
Open Document
      ↓
Permission Check
   ↙        ↘
Allow      Deny
```

If meaningful failure paths exist → document them.

---

### 7 — Is the workflow reused?

Example:

```text
Request Access
```

might appear on:

* Projects
* Client Hub
* Communities
* Leadership areas
* Documents

Instead of creating five diagrams:

Create:

**WF-ACCESS-001 — Request Access Workflow**

Then pages reference it.

---

# 7. Workflow Scoring

We can make the decision almost mechanical.

Give the workflow **1 point** for each:

* Multiple actors
* Permission check
* Decision branch
* Data write
* External integration
* Failure state
* Reused by several pages

### Score

**0–1**

No SVG.

---

**2–3**

Document briefly in the page specification.

---

**4+**

Create a dedicated SVG workflow.

# 13. Define Claude Code Rules

This is one of the most important parts.

Claude will receive explicit rules such as:

### Before coding

* Inspect existing components.
* Inspect existing routes.
* Inspect dependencies.
* Check whether the required component already exists.
* Read the relevant page specification.
* Read referenced workflows.

### While coding

* Reuse before creating.
* Never duplicate shared components.
* Never put authorization only in UI logic.
* Keep page components small.
* Separate data logic from presentation.
* Keep responsive behavior.
* Preserve established design tokens.

### After coding

* Run build.
* Check errors.
* Test responsive layouts.
* Check loading state.
* Check empty state.
* Check error state.
* Check restricted state.
* Check navigation.
* Check component reuse.
